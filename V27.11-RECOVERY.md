# v27.11 - Missed-slot recovery + Mix-mode gap fill

Applies to `zedge1.yml` / `zedge2.yml` / `zedge3.yml` (identical logic in all three), the web panel
(`index.html`), the desktop app (`desktop/`) and the Android app (`app/`).

## 1. A slot whose upload did not happen is uploaded again - always 3 uploads a day

**Before:** the gate marked a slot "done" the moment it released the run. If the automation job then never
ran (GitHub Actions outage, runner never started, YAML/step error) or crashed before the file was added and
the *Upload* button clicked, that slot was silently lost for the day - the panel even showed it as uploaded.

**Now**

* `bot.js` reports the *real* result of every upload into the slot's run marker
  `dashboardSettings/gate/runs/<YYYY-MM-DD>/<slot>`:
  `status: started -> uploaded | failed | idle | skipped-limit` (+ `error`, `itemId`, `title`, `attempts`,
  `retry`, `plan`, `finishedAt`). A workflow step (`🛟 Report unfinished slot(s)`) flips a marker that is still
  `started` to `failed` when the job fails or is cancelled before `bot.js` could report.
* The gate (every 30-min ping) classifies each slot: `done` (uploaded / skipped-limit / legacy marker),
  `running` (`started` < 70 min ago), `failed` (failed / idle / stale `started` / never ran and its window is
  over), `none`. A `failed` slot with `attempts < 3` and fewer than 3 uploads today is **missed** and:
  * **still inside its window** -> retried on the next ping (decision `retry`);
  * **window already over, another window still ahead today** -> merged into that window's run: the gate
    outputs `slots=[next, missed]`, `count=2`, and `bot.js` uploads **2 files** in that run
    (`UPLOADS_PER_RUN`); the daily cap of 3 is still enforced;
  * **window over and no window left today** -> run on the next ping (`retry-late`), so the day's third
    upload still happens before midnight;
  * after **3 attempts** the gate gives up for that slot and says so.
* **Notifications** - once per miss (per attempt/plan), to the panel, desktop app and Android app via
  `dashboardSettings/alerts/<id>` (`{ts, kind, text, textBn, slot, attempts, plan, source}`) and to Telegram:
  *"Slot 2 (15:22) was not uploaded at its scheduled time: upload failed - Upload button not found. It will be
  uploaded in the next window - Slot 3 (20:05) - together with that slot's file."* When the retry succeeds the
  bot posts *"Slot 2 recovered: "<title>" was uploaded at 20:07 (retry)."*
  * Web: notification center + toast (48 h look-back, seen-ids in `localStorage zedgeAlertSeen:v27`).
  * Desktop: notification center + toast (`NotificationCenter.addRemoteAlerts`, seen-ids in SharedPreferences).
  * Android: system notification (channel *Upload slot alerts*) + in-app snackbar (`QueueRepository.alerts`).
* **Status everywhere:** today's run strip / overview cards show `MISSED · RETRY` (with the reason and the
  plan), `RUNNING`, `DONE (recovered)`; `W1 10:27 (FAILED · retry pending)` in the schedule health line. Only
  a real `uploaded` counts as done now.
* `dashboardSettings/gate.recovery` = `{enabled, uploadsDone, missed[], plan, nextSlot, states[]}` for debugging.
* Switch off: `dashboardSettings/schedule.retryMissed = false`. Force runs (`force_run=true`) are unaffected
  (no gate slot -> nothing to report).

Constants (gate): `STALE_RUN_MIN = 70`, `MAX_ATTEMPTS = 3`, `DAILY_LIMIT = 3`.
New gate outputs: `slots`, `count`, `retries`; new bot env: `GATE_SLOTS`, `GATE_RETRY_SLOTS`, `UPLOADS_PER_RUN`.
The Telegram token/chat env was added to the gate step (same defaults as the bot step).

## 2. Mix mode - no empty slot when only some content types have files

**Before:** with mix mode ON and e.g. only Ringtone + Wallpaper files queued, slot 3 wanted the third type,
found no stock and threw `MIX_MODE_WAIT` -> only 2 uploads that day (strict mode waited on purpose, and even
non-strict mode failed when *unused* types were empty).

**Now (`getNextWallpaperFromRealtimeDB`, GAP FILL):** if none of the wanted (unused) types has stock the bot
takes the type with the **fewest uploads today** that still has files (ties -> today's order) and logs
`MIX_MODE => ... [GAP FILL ...]`. This applies in strict mode too - *strict* now only sets the preference
("different type first"); a slot is never left empty. `MIX_MODE_WAIT` is thrown only when **no** type has a
queued file at all (then the missed-slot recovery above retries the slot as soon as files are added).

The desktop calendar planner (`schedule_planner.dart`) mirrors the gap fill, and the Strict checkbox text in
the panel / desktop / Android now reads *"prefer a different type for every slot (repeats only when no other
type has stock - a slot is never left empty)"*.

## Versions
desktop `27.11.0+6`, Android `2.3.0 (3)`.

## v27.11.1 hotfix - "Invalid workflow file ... Exceeded max expression length 21000"
GitHub treats a `run:` block that contains any `${{ }}` as ONE expression, and expressions are capped at 21 000 chars.
The v27.11 gate step (`zedge1/2/3.yml`, "Smart upload gate") grew past that with `${{ inputs.force_run }}` inside it, so
GitHub rejected the whole file before running anything. Fix: the value is now passed as an env var
(`FORCE_RUN: ${{ inputs.force_run }}` -> `if [ "$FORCE_RUN" = "true" ]`). No logic changed. Replace `.github/workflows/main.yml`
(or the zedgeN.yml you use) with the new file.

## v27.11.2 - fewer extra runs (GitHub Actions minutes)
Since v27.11 a slot whose upload did not happen was re-run inside the same window up to 3 times - also when the reason was
simply "nothing to upload" (idle). That can triple the number of runs per day and burn the account's Actions minutes
(Windows runners count double on private repos). Now:
* only a REAL technical failure gets ONE extra run inside its own window;
* "idle" / "never started" / 2nd failure are NOT re-run in the window - they are merged into the NEXT window's run
  (`count=2`, zero extra runs), exactly like a slot whose window is already over;
* late catch-up (no window left today) is unchanged.
Verified with the mock-Firebase harness (retry / next-window / merged / blocked scenarios).

## v27.11.2 - no more "stuck for hours" runs
Runs were sitting for a long time at "Waiting for login success bell icon" / "Waiting for Edit meta button" and had to be
cancelled by hand. Those Playwright waits had NO timeout (`context.setDefaultTimeout(0)`), so when Zedge showed a
captcha / verification page or its upload processing stalled, the run hung forever and the slot was lost.
* Login: fails after **4 min** with `LOGIN_STUCK => ...` (URL + page text + `zedge-login-stuck.png`).
* Edit meta (after the file upload): bounded to **10 min**.
* Job level: `timeout-minutes: 90` on the automation job as a safety net.
In every case the slot is reported as **failed** -> Telegram / panel alert -> the file is uploaded again in the next window
(merged, no extra run) or as a late catch-up. Nothing else in the upload flow changed.

## v27.11.3 - login success detection no longer depends on the bell icon
**Problem:** after a correct login the bot waited for `svg[data-icon="bell"]`. Zedge often renders the earnings
dashboard without (or long before) the bell icon, so the bot sat there for 4 minutes and failed with `LOGIN_STUCK`
although the account was logged in.

**Fix (all `zedge1-4.yml`, bot.js login step):** `page.waitForFunction(loginSuccessSignal, ...)` - login is accepted
as soon as ANY of these is visible (checked every 500 ms, still max 4 min):

| signal | what is checked |
|---|---|
| `dashboard-period-picker` | `input[name="period"]` (YYYY/MM/DD - YYYY/MM/DD) + "Dashboard" text |
| `dashboard-revenue-cards` | a `<span>` whose text is `UNLOCKS`, `USERS` or `NET REVENUE` |
| `dashboard-profiles-filter` | `input[name="profiles"]` or "All profiles" text |
| `bell-icon` | `svg[data-icon="bell"]` (old check, kept) |
| `profiles-nav-link` | visible `a[href*="/profiles"]` while no login form is open |
| `profiles-url` | URL already on `/profiles...` while no login form is open |

The log prints `✅ Login success detected via: <signal>`. If the login form is still open and the page shows an error
text (invalid/incorrect password, account locked, too many attempts, verify your email, captcha) the run fails
immediately with `LOGIN_FAILED => ...` instead of waiting 4 minutes. The same detection is used by the
"Zedge Flow Tester" Chrome extension.

## v27.11.4 - login confirmed by the Zedge auth API (from HAR of a logged-in session)
The HAR of a logged-in `upload.zedge.net` session shows what the SPA does right after login:

| request | response when logged in |
|---|---|
| `POST https://upload.zedge.net/auth/token` body `{"scope":"user"}` | `{"accessToken":"<jwt>","expiresAt":...}` |
| `GET https://upload.zedge.net/auth/user-info?scope=user` | `{"expiresAt":...,"email":"<account email>","username":"<name>","grants":[]}` |
| `POST https://api-gateway-v2.zedge.net/` (GraphQL `businesses`, `profiles`, `notifications`, `insightsTotalsAsUser`...) | header `x-auth-v2: <accessToken>` |

Both auth calls are driven by the httpOnly session cookie, so they are the definitive "this browser is logged in" proof
- no UI element needed.

**bot.js login step now (all `zedge1-4.yml`):**
1. `page.on("response")` is registered before "Continue with Email" - a `200` from `/auth/user-info` with `email`
   (or `/auth/token` with `accessToken`) marks the login as confirmed (`network:/auth/user-info`).
2. Every 2 s the bot itself calls `fetch("/auth/user-info?scope=user", {credentials:"include"})` inside the page -
   `{email}` back = logged in (`api:/auth/user-info`).
3. DOM signals from v27.11.3 (dashboard period picker, UNLOCKS/USERS/NET REVENUE, All profiles, Profiles link,
   `/profiles` URL, bell icon) stay as fallback (`dom:*`).
4. Login error text while the login form is open -> `LOGIN_FAILED` immediately.
5. Still nothing after 4 min -> `LOGIN_STUCK` + `zedge-login-stuck.png`.

Log line: `✅ Login success detected via: api:/auth/user-info (account you@mail.com)`.
The Chrome extension "Zedge Flow Tester" uses the same `/auth/user-info` probe (step 3 and step 5).
